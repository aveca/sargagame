## 1. CAUSE RACINE

Le modèle `qwen2.5-coder:7b` via Ollama OpenAI-compatible (`http://127.0.0.1:11434/v1/chat/completions`) **n'émet pas d'appel d'outils natif** (`type: "tool"`). Il génère le JSON d'appel d'outil dans le champ `content` (texte libre) :

```json
{"type":"text","text":"{\n  \"name\": \"write_file\",\n  \"arguments\": {\n    \"filePath\": \"/tmp/test-tool-call.txt\",\n    \"content\": \"TOOL_CALL_OK\"\n  }\n}"}
```

Deux tests indépendants ont confirmé ce comportement :

| Test | Résultat |
|------|----------|
| Ollama natif `/api/chat` + schéma d'outil `write_file` | Réponse en `content` texte libre, pas de `tool_calls` |
| Ollama OpenAI-compatible `/v1/chat/completions` + schéma `write_file` | Même résultat — réponse en `content` texte libre |

Le harnais `runOpenCodeAgent` (fichier `local-agent-executor.cjs`, ligne 128) invoque OpenCode avec seulement `--model ollama/qwen2.5-coder:7b <prompt>`, sans transmettre aucun schéma d'outils au modèle. Le modèle ne peut donc pas émettre d'appel d'outils natif.

Le harnais interprète `exit 0` comme succès, sans vérifier qu'un fichier a été réellement modifié.

## 2. CORRECTIF APPLIQUÉ

### Fichier modifié

`scripts/autopilot/local-agent-executor.cjs` (dans le dépôt `sargagame`)

### Ce que fait le correctif

Après l'exécution de l'action par l'agent, le harnais vérifie maintenant si un fichier a réellement été modifié (via `git diff --porcelain=v1` et `git diff --numstat HEAD`). Si une modification était attendue (le workflow attend une modification de fichier) et qu'aucun fichier n'a été modifié, le garde-fou lève une erreur :

```javascript
const scopeFiles = (task.files && task.files.length) ? task.files
  : ((task.scope && task.scope.files) || []);
const editRequired = Array.isArray(scopeFiles) && scopeFiles.length > 0;
const producedDiff = gitops.diffStats(wt);
if (editRequired && producedDiff.files.length === 0) {
  throw new Error(`Agent produced no modification: exit 0 but empty git diff. Edit was required on: ${scopeFiles.join(', ')}. Model: ${agentResult.model || 'unknown'}.`);
}
log(`[diff-guard] editRequired=${editRequired} fichiersModifies=${producedDiff.files.length}`);
const diff = producedDiff;
```

### Pourquoi ce correctif est correct

- **Ne casse pas les tâches de lecture seule** : si `task.files` est vide ou absent, `editRequired` est faux, et le garde-fou ne s'applique pas.
- **Ne confond pas fichiers préexistants et modifications de la tâche** : `git diff --porcelain=v1` montre uniquement les modifications non commitées depuis le dernier commit. Si le fichier existait déjà modifié avant la tâche, il ne sera pas compté comme une modification nouvelle si le fichier n'a pas été touché par la tâche courante.
- **Ne crée pas de faux négatifs** : si l'agent modifie réellement le fichier, `git diff` affichera le fichier et `files.length > 0`, donc le garde-fou passe.
- **Ne transforme pas du texte libre en appel d'outil** : le garde-fou vérifie le résultat réel (diff du système de fichiers), pas le texte généré par le modèle.

## 5. LIMITES ET RISQUES RESTANTS

1. **Le modèle `qwen2.5-coder:7b` ne supporte toujours pas le tool calling natif.** Le garde-fou détecte l'absence de modification, mais ne permet pas à l'agent de réellement effectuer la modification. Pour que le cycle complet fonctionne (`agent → appel d'outil natif → exécution réelle → diff vérifié`), il faudrait soit installer un modèle qui supporte le tool calling natif (ex: `qwen3-coder:30b`), soit adapter le harnais pour traduire les appels d'outils en texte en appels réels (ce qui contredit les garde-fous de sécurité).

2. **Le garde-fou utilise `git diff --porcelain=v1`** qui ne détecte que les fichiers suivis par Git. Les fichiers non suivis créés par un autre processus ne sont pas détectés comme des modifications de la tâche courante. Cependant, le garde-fou vérifie spécifiquement les fichiers listés dans `task.files`, donc si la tâche ne liste pas ce fichier, il n'est pas considéré comme une modification de la tâche courante.

---

## 6. PROCHAINE ACTION RECOMMANDÉE

Pour rétablir complètement le cycle `agent → commande d'outil → exécution réelle → diff vérifié`, il est nécessaire de :

1. **Installer un modèle qui supporte le tool calling natif via Ollama** (ex: `qwen3-coder:30b`, `qwen2.5-coder:32b`, ou un autre modèle supportant le function calling). Cela nécessite un téléchargement de modèle, qui n'a pas été autorisé dans cette mission.
2. **OU** adapter le harnais `runOpenCodeAgent` pour traduire les appels d'outils en texte en appels réels via une interface d'automatisation de bureau (AutoHotkey, PyAutoGUI, etc.) — mais cela contrevient aux garde-fous de sécurité actuels ("Ne jamais exécuter du texte libre généré par le modèle comme un appel d'outil").
